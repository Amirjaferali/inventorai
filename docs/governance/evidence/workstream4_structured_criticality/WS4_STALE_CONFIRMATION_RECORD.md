# WS4_STALE_CONFIRMATION_RECORD — stale-confirmation surfacing

## 1. Deterministic example

`ws4_stale_confirmation.json` (generated by `generate_ws4_artifacts.py`):
on a completed real WS1 journey, one explicit deferral is recorded for the
deterministically never-generated requirement id `req:assertion:rec_999`
(state-level recorder call — the same committed technique the test suite
uses). The harness then proves, with hard assertions that abort the whole
evidence run on failure:

- the id is NOT among the generated landscape requirement ids (genuinely
  stale);
- **not reattached**: every generated requirement keeps
  `system-derived` authority — the stale record applies to nothing
  (`derive_requirement_landscape` applies a confirmation only to the exact
  `requirement_id` it was recorded for);
- **aggregate metadata only**: the deliverable carries
  `_session_meta.stale_criticality_confirmations = {"total": 1, "note": <fixed
  truthful sentence>}`;
- **no raw stale requirement id exported**: the full serialized package
  contains zero occurrences of the stale id (machine-scanned);
- the record itself remains retained in the session-bounded history
  (append-only traceability).

## 2. Placement rationale (contract compatibility)

Section 13's exact key set is frozen by the committed assertion
`tests/test_phase_7c_requirement_landscape_collapse.py:129`; placing stale
metadata inside section_13 would have required an existing-assertion change,
which only the literal hygiene amendment was authorized to make. The
aggregate metadata therefore lives under `_session_meta` — the committed
precedent for additive nesting "so the top-level canonical-section contract
is unchanged" (evidence_registry, unknown_registry,
inventor_stated_safety_signals). `web/templates/deliverable.html` was not
modified for stale display, per the owner evidence authorization ("Do not
modify deliverable.html merely to show stale metadata").
