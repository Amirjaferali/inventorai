## PURPOSE

This document classifies existing project commitments by type.
It does not create new commitments. It does not authorize anything.
It maps what already exists so that the nature of each commitment
is explicit and cannot be misread.

The question this document answers:
> "What kind of commitment is each existing project commitment?"

Classification rationale is provided for each commitment.
Misclassification risks are identified where significant.

---

## COMMITMENT TYPES USED

Definitions are derived from the commitments themselves, not
imported from external frameworks. Only types needed to classify
existing commitments are used.

**Constitutive Commitment:**
Defines what the platform is. Changing it would make the platform
a different thing, not a better version of the same thing.
These cannot be relaxed without owner decision at Level 0.

**Protected Commitment:**
Must not be modified without explicit authorization and evidence.
Protects against drift, premature change, or scope expansion.
Violation requires review before proceeding.

**Objective:**
A measurable outcome the platform is designed to produce.
Not a rule about how -- a statement about what.

**Preference:**
A design orientation that guides choices when multiple options
are available. Does not prohibit alternatives absolutely.
Can be overridden with justification.

**Strategic Option:**
A possible future direction that is not yet authorized.
Must not be treated as a commitment until explicitly converted
by owner decision with evidence basis.

**Evidence Requirement:**
A condition that must be demonstrated before a next step
can be authorized. Not a commitment to take the step -- a
commitment to require evidence before taking it.

## SECTION 1 -- CONSTITUTIVE COMMITMENTS

These define what InventorAI is. They cannot be modified without
changing the platform's identity.

---

### C-1 -- Inventor Owns Content; Platform Owns Structure

**Source:** STRATEGIC_PRODUCT_VISION.md §10, §2 Substitution Prohibition;
SA-001B §2.4 (read verbatim this session)

**Commitment:**
The inventor owns all reasoning, all content, and all conclusions.
The platform owns only the structure of questioning and the gating
criteria. These two ownership domains must never be merged.

**Classification rationale:**
This is constitutive because it defines the relationship between
the platform and the inventor. A platform that generates content
on the inventor's behalf is a different product, not a modified
version of this one. Relaxing this commitment changes what
InventorAI is.

**Preservation requirement:**
No output generated by AI may enter the session record as
inventor-demonstrated knowledge. idea_summary is explicitly
blocked from AI generation. AI Echo (platform content
re-entering the record as inventor knowledge) is a governance
violation, not a design option.

**Misclassification risk:**
This is sometimes described as a "preference for inventor-led
sessions." It is not a preference. It is constitutive. Treating
it as a preference allows incremental erosion: the platform
"helps" formulate responses, then "suggests" revisions, then
generates on behalf of the inventor. Each step appears small;
the cumulative effect is a different product.

---

### C-2 -- AI May Not Control Progression

**Source:** ARCHITECTURE_GUARDRAILS.md §8 (read verbatim this session)

**Commitment:**
AI MAY: classify, summarize, recommend, explain.
AI MAY NOT: decide maturity, close gaps, issue PASS/BLOCK,
control state.

evaluate_transition(), integrate_response(), assess_response()
must remain pure and deterministic. No AI calls permitted. Ever.

**Classification rationale:**
This is constitutive because it defines the authority model of
the platform. A platform where AI decides advancement is a
different platform -- one where the platform's judgment replaces
the inventor's demonstrated understanding. The deterministic
gate is what makes the platform's output trustworthy as evidence
of inventor capability.

**Preservation requirement:**
The three named functions must never call AI. This is an
architectural invariant enforced by ARCHITECTURE_GUARDRAILS.md
§8 and verified by WPS001 INV-007.

**Misclassification risk:**
This is sometimes framed as an "AI boundary preference" or
"current design choice pending future review." Neither framing
is correct. The commitment is permanent per its source document.
GD-002 (Technical Guidance Without Decision Ownership) remains
a governance proposal because the boundary between advisory and
controlling has not been resolved -- it does not relax C-2.

---

### C-3 -- Engine Independence from Domain

**Source:** ARCHITECTURE_GUARDRAILS.md §1, §2, §4 (read verbatim)

**Commitment:**
progression_loop.py must not know domain names directly.
Domain-specific branching in the engine is permanently forbidden.
Adding a new domain must require zero changes to progression_loop.py.

**Classification rationale:**
This is constitutive because it defines the separation between
reasoning structure (engine) and domain knowledge (domain layer).
A platform where the engine contains domain logic is architecturally
a different system -- one that cannot scale to new domains without
engine modification.

**Preservation requirement:**
Verified by ARCHITECTURE_GUARDRAILS.md §12 TEST 1 and TEST 2.
AB-006 closure (commit aa47149) confirmed this invariant holds.
git diff on engine files must show zero domain-specific branching.

**Misclassification risk:**
This is occasionally described as a "current architectural choice"
subject to revision. It is not. The guardrails document explicitly
states "this rule applies permanently" and requires architectural
review before any violation.

## SECTION 2 -- PROTECTED COMMITMENTS

These must not be modified without explicit authorization and
evidence. They protect the platform against specific failure modes.

---

### P-1 -- MVP Scope Freeze

**Source:** MVP_SCOPE_FREEZE.md (read verbatim this session)

**Commitment:**
The freeze defines what is in scope and what is frozen out.
It expands only after specific revision criteria are met:
3 real ideas tested through LEVEL 0-2, at least 1 genuine BLOCK
understood, at least 1 idea reached LEVEL 2 with documented
clarity improvement.

**Classification rationale:**
Protected, not constitutive. The scope freeze is designed to be
lifted when evidence warrants it. But it cannot be lifted
informally, incrementally, or without meeting the stated criteria.
It protects against premature complexity.

**Current status:**
Revision criteria are not yet formally met. ILT-002 is the first
serious attempt to generate evidence against the criteria. Four
active domains exist in the repository despite the freeze stating
"electronics/electrical inference only" -- this is an acknowledged
inconsistency that requires formal freeze revision to resolve.

**Misclassification risk:**
The freeze is sometimes treated as already superseded because
multiple domains exist in code. Code existence does not constitute
formal freeze revision. The revision protocol must be explicitly
executed and committed.

---

### P-2 -- WPS001 Benchmark Stability

**Source:** handover_summary §5, §6; ARCHITECTURE_GUARDRAILS.md §12

**Commitment:**
WPS001 must remain at 20 passed / 0 failed. Variance must be 0%.
AI assertion must be verified as disabled during benchmark.

**Classification rationale:**
Protected. This is the primary regression guard for the engine.
It can be expanded (new tests added) but cannot be allowed to
degrade without investigation and explicit authorization.

**Current status:** Verified at current HEAD. 20 passed, 1 skipped,
3 warnings (all expected and documented).

---

### P-3 -- Evidence Freeze on ILT-002 Records

**Source:** SESSION3_EVIDENCE_FREEZE.md; ILT002_EXECUTION_GUIDE.md §9 Rule 4

**Commitment:**
Past session records cannot be revised based on later observations.
Factual corrections only, initialed and dated. Session 3 baseline
is frozen. Idea A Session 1 transcript is committed.

**Classification rationale:**
Protected. Evidence integrity requires that classifications made
at classification time cannot be retroactively adjusted. The freeze
makes the evidence base reliable.

---

### P-4 -- Idea A Timing Table Lock

**Source:** ILT002_EXECUTION_GUIDE.md §9 Rule 5;
ILT002_EMERGENCE_TIMING_TABLE.md Part 1

**Commitment:**
Idea A timing table must be locked before any Idea B sessions
occur after Idea A begins. Once locked, Part 1 cannot be modified.

**Classification rationale:**
Protected. The lock prevents retroactive adjustment of Idea A
timing to produce favorable S-6 comparisons. It is an evidence
integrity mechanism.

**Current status:** Not yet locked. Idea A Session 1 is complete.
Lock must occur before any additional Idea B sessions.

---

### P-5 -- No Prototype or Technical Package Generation

**Source:** STRATEGIC_PRODUCT_VISION.md §5B; SA-001A §5

**Commitment:**
FDC-001 does not prove implementation readiness. The platform does
not generate prototype specifications, engineering packages, or
technical decisions on behalf of inventors. Completion of the
platform protocol is not equivalent to invention readiness.

**Classification rationale:**
Protected. Without this commitment, the platform's output could
be misrepresented as engineering validation. FDC-001 is an
evidence record of inventor articulation, not a technical authority
document.

## SECTION 3 -- OBJECTIVES

These are measurable outcomes the platform is designed to produce.
They are not rules -- they are statements of purpose.

---

### O-1 -- Inventor Articulation Improvement

**Source:** MVP_SCOPE_FREEZE.md SUCCESS CRITERION

**Commitment:**
After 3-5 iterations: the inventor articulates their idea more
precisely than when they started.

**Classification rationale:**
Objective. Specific, observable through transcript comparison,
and bounded. It is the operationalized version of the deeper
SR-001 objectives for the current MVP scope.

**Current measurement status:**
Partially measurable through specificity test applied to transcripts.
Not yet systematically measured across the full campaign.

---

### O-2 -- Inventor Development Across Four Dimensions

**Source:** SR-001_INVENTOR_OUTCOME_MEASUREMENT.md §2.1;
STRATEGIC_PRODUCT_VISION.md §2

**Commitment:**
The platform measures and grows: reasoning quality, ownership depth,
gap precision, implementation readiness proximity.

**Classification rationale:**
Objective. These are the governing dimensions of inventor improvement
per Level 0 authority. They are the defined success criteria for
the platform's purpose, not aspirations.

**Current measurement status:**
Partially measurable (reasoning quality via REASONED/ASSERTED,
gap precision via gap state trajectory). Ownership depth and
implementation readiness proximity are not yet measurable with
current infrastructure.

---

### O-3 -- Deterministic and Reproducible Progression

**Source:** DECISION_PROGRESSION_MODEL.md §11; handover_summary §5

**Commitment:**
Same idea twice produces identical IdeaState. The engine is
deterministic. Progression decisions are not probabilistic.

**Classification rationale:**
Objective. Reproducibility is what makes the platform's output
usable as evidence. A non-deterministic engine produces results
that cannot be compared across sessions.

**Current status:** Verified. WPS001 INV-007 tests determinism.

## SECTION 4 -- PREFERENCES

These guide design decisions without absolutely prohibiting alternatives.

---

### PR-1 -- Evidence Before Implementation

**Source:** Project governance discipline throughout; CLAUDE.md

**Commitment:**
Governance and evidence precede implementation. No implementation
work begins before the governing framework is established and
the evidence basis is understood.

**Classification rationale:**
Preference, not constitutive. The project has consistently applied
this sequencing. But the preference is not an absolute prohibition
on opportunistic implementation where evidence already exists and
scope is frozen.

---

### PR-2 -- Minimal Change Principle

**Source:** CLAUDE.md engineering rules; master_context

**Commitment:**
Prefer the smallest possible change that fixes the root cause.
No unrelated refactoring. No architecture changes without root
cause evidence.

**Classification rationale:**
Preference. It reduces risk and preserves historical behavior --
but can be overridden when larger changes are warranted and
explicitly authorized.

---

### PR-3 -- Single Question Per Iteration

**Source:** DECISION_PROGRESSION_MODEL.md §8; MVP_SCOPE_FREEZE.md

**Commitment:**
One question per iteration, traceable to an open gap.
No embedded second questions.

**Classification rationale:**
Preference with protective intent. Operationally enforced by the
engine -- but as a design preference it can be revisited if evidence
shows a different structure is more effective. Not constitutive.

## SECTION 7 -- RELATIONSHIPS BETWEEN COMMITMENTS

**C-1 and C-2 constrain all strategic options.**
Any future layer (SO-2, SO-3) must be designed within C-1
(inventor owns content) and C-2 (AI cannot control progression).
These are not negotiable constraints on future options -- they are
constitutive of the platform that any future option must extend.

**Protected commitments enforce evidence requirements.**
P-3 (evidence freeze) and P-4 (timing table lock) protect the
integrity of ER-1 (ILT-002 before classification). Without evidence
integrity, the classification cannot be trusted.

**Strategic options depend on objective achievement.**
SO-2 (Engineering Assessment) depends on O-2 (Inventor Development)
being demonstrated. Adding complexity before objectives are met
adds cost without confirmed foundation.

**Preferences can be overridden; constitutive commitments cannot.**
PR-1 (evidence before implementation) is a preference and can be
overridden in bounded circumstances. C-1 through C-3 cannot be
overridden -- they define what the platform is.
