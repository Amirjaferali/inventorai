## 0. Governing product principle and rejected interaction pattern

**[OWNER]** InventorAI is not a questionnaire, examination, assessment form, or static workflow. It is an intelligent working partner that understands what the inventor already knows, organizes the inventor's thinking, identifies only the missing information, asks the smallest useful next question, proposes structured interpretations, allows confirm/correct/defer, and reduces cognitive burden. The interaction must not be designed as "the user supplies everything / the platform only records answers." Learning from the previous platform (fixed questions → fixed answers → AI analysis → immediate MVP/risk/pitch/IP outputs, whose core failure was generating advanced outputs before confirming correct understanding), **this contract explicitly rejects**: identical questions for every inventor; no answer-driven follow-up; no confirmation of what the platform understood; re-asking for already-provided information; generating advanced outputs from incomplete or misunderstood answers; requiring answers merely to complete a field. Every requirement below is bound by this principle, applied within the Workstream 4 scope boundary of §17.

## 3. Required behavior

**[OWNER + PROPOSED]** Within the criticality flow, the platform acts as a working partner: it first establishes and **confirms its understanding** from what the inventor has already said; it then presents a concise summary-first proposal of what appears essential and what appears adjustable, grounded in attributed inventor statements; the inventor confirms with one lightweight action, corrects exceptions, answers at most one short supportive clarification at a time, or defers; every explicit action is recorded in an append-only confirmation history within the active session state; the pure derivation emits: confirmed → category / `owner-confirmed` / verbatim rationale; explicitly deferred → `UNDETERMINED` / `undetermined`; never interacted → `UNDETERMINED` / `system-derived` (status quo preserved). No proposal is adopted silently; no advanced classification is produced from misunderstood or unconfirmed core input; nothing already provided is requested again; no technical knowledge is demanded; historical sessions are never rewritten.

## 4. Definitions (binding)

- **Canonical categories [CANONICAL, C4-R4]:** `FEASIBILITY-THREATENING`, `VALUE-ENHANCING`, `REFINEMENT`, `UNDETERMINED` — category strings, never scores, internal-only.
- **Authority model [OWNER; evaluation in §16.1]:** never-interacted → `UNDETERMINED`/`system-derived`; explicitly deferred → `UNDETERMINED`/`undetermined`; explicitly confirmed non-`UNDETERMINED` → selected category/`owner-confirmed`. `specialist-confirmed` out of scope. No system output may ever be represented as `owner-confirmed` without explicit inventor acceptance (C4-R5). **Clarification (owner-authorized, PR #181 review):** a `confirmed` action may carry exactly one of `FEASIBILITY-THREATENING`, `VALUE-ENHANCING`, or `REFINEMENT`; `confirmed + UNDETERMINED` is invalid and must be rejected; uncertainty or a decision not to classify must use the `deferred` action, which carries no category and derives `UNDETERMINED`/`undetermined`.
- **Understanding context [OWNER]:** the platform's working picture of the idea, the problem, who experiences it, the current situation, the desired result, the relevant requirement, and why it exists — assembled from the inventor's natural explanations already recorded in session state (idea text, `idea_summary`, ledger records, gap evidence, acknowledged unknowns). These are understanding **goals**, not mandatory fields: points already provided in any answer are reused, never re-asked.
- **System proposal [OWNER]:** a prepared, explicitly-unconfirmed interpretation `{requirement_id(s), proposed category, proposed rationale = an attributed verbatim inventor statement, simple-language explanation}`. Formed only when grounded in attributable displayed inventor context; keyword matching alone can neither form nor adopt one; it affects nothing until accepted.
- **Inventor confirmation / correction / deferral:** the explicit inventor actions; only these create recorded state.
- **Recorded owner-confirmed result:** the append-only record produced by confirmation — the only thing derivation may treat as `owner-confirmed`.
- **Public wordings [OWNER]:** `FEASIBILITY-THREATENING` → "Essential to feasibility"; `VALUE-ENHANCING` → "Important to value"; `REFINEMENT` → "Refinement or improvement"; `UNDETERMINED` → "Not yet determined"; `owner-confirmed` → "Confirmed by the inventor"; `undetermined` → "Confirmation not yet available"; `system-derived` → the existing committed wording (unchanged). Raw internal tokens never appear inventor-facing — deliverable or UI.
- **Stale confirmation:** a recorded action whose `requirement_id` is no longer generated; surfaced honestly, never silently reattached.

## 6. Recorded-state model (session-bounded, append-only)

**[PROPOSED]** Additive, in `engine/idea_state.py`, living entirely inside the in-memory `IdeaState` — an **append-only confirmation history within the active session state**. Nothing here survives application restart, session loss, or historical reload, and no durable retention is implied or introduced (persistence remains frozen; no schema migration):

1. `IdeaState.criticality_confirmations: list[CriticalityConfirmation]` — one frozen record per explicit inventor action: `{confirmation_id (append-order), requirement_id, action ∈ {confirmed, deferred}, category (for confirmed: exactly one of FEASIBILITY-THREATENING, VALUE-ENHANCING, REFINEMENT — never UNDETERMINED; None for deferred), rationale_verbatim (required non-empty for any non-UNDETERMINED confirmation; byte-verbatim), rationale_source ∈ {reused_statement:<record_id>, inventor_edited, inventor_typed}, iteration, provenance="owner_confirmed"}`. Records are never mutated or removed within the session; later actions supersede by ordering only, and earlier active-session records remain available for traceability.
2. **Current lookup** — latest record per `requirement_id` (recomputed or maintained) for derivation/rendering; the latest explicit action governs the current derived result.
3. **Guarded recorder** — `record_criticality_confirmation(...)`: validates the category vocabulary; rejects `action=confirmed` with `category=UNDETERMINED` (an invalid combination that BOTH the recorder and the route must reject — nothing stored); rejects non-`UNDETERMINED` without a non-empty rationale; stores rationale byte-verbatim; affects nothing else (no gaps, maturity, transitions, ledger content, Evidence, transcript, scoring).
4. **Derivation** — `derive_requirement_landscape` (imports only `engine.idea_state`) applies the §4 authority model from the current lookup; `DerivedRequirement` remains a frozen, stateless render-time derivation.
5. Inventor originals stay verbatim and separately preserved; a reused rationale is an attributed copy, never a rewrite. Platform-prepared interpretations are never stored as inventor-authored facts absent explicit confirmation **[OWNER]**.

## 7. Confirmation interaction (working-partner flow)

**[OWNER + PROPOSED]** A lightweight step integrated into the existing journey near completion / before final deliverable generation (route/placement implementation-chosen; no separate heavy classification page; no long mandatory per-requirement form as default **or** fallback):

1. **Understanding before classification.** The step may run only when the understanding context (§4) for the affected requirement exists from the inventor's recorded explanations. No criticality question is presented before its requirement has been made understandable; criticality is positioned as a natural continuation of the earlier discussion, never a disconnected classification exercise. Where context is insufficient, the flow goes to §7.4/§7.5 (clarify or defer) — never to classification.
2. **Summary-first.** Before any criticality is adopted, the platform presents a concise, natural-language summary of what it understood — of the form: *"This is what I understood from your explanation: the problem is…; the intended result is…; this part appears essential because…; this part appears adjustable because…. Is that correct?"* — with the lightweight actions **Yes, that is correct · Change this part · Something is missing · I am not sure yet · Decide later**. The summary is short; the inventor is never required to review a large document.
3. **Guarded grouped confirmation.** One summary-level action may cover multiple requirements only when they genuinely share the proposed category, the rationale, **and** the inventor context; every covered requirement is visibly listed or easily inspectable; the shared category and shared reason are visible; any item can be opened, individually corrected, or individually deferred; unrelated or materially different requirements are never grouped merely to reduce clicks. Fewer unnecessary actions — not blind bulk approval.
4. **Grounded proposals; no-proposal fallback.** Where a grounded proposal exists: show it, explain it in simple language, offer confirm/edit/defer. Where none exists: do not guess, do not show a long form; ask **one** short supportive clarification in inventor-facing language (e.g. *"Would the idea still achieve its purpose if this part changed?"* or *"Would the idea fail without this part?"*) or preserve `UNDETERMINED` and let the inventor continue. No category codes or governance terminology anywhere.
5. **Adaptive sequencing.** Within this flow, questions are never a fixed list: each cycle is *inventor answer → update what is known → identify the most important missing information → ask one relevant next question → use the answer*. The next question depends on the preceding answer; unrelated questions are never batched; nothing is asked "because it is next." Before asking anything, the platform checks prior inventor answers, recorded evidence, the relevant requirement, earlier confirmations, and existing rationales — already-known information is reused or shown for confirmation, never requested again.
6. **No technical burden.** The flow never requires technical architecture, hardware/software stack, implementation method, engineering mechanism, feasibility analysis, component design, or MVP structure. Platform-derived technical interpretations, where later produced, are platform contributions and are never represented as inventor-authored facts without explicit confirmation where confirmation is required.
7. **Rationale reuse.** An existing verbatim statement containing the reason is displayed as the proposed rationale with **Confirm** / **Edit**; stored (as an attributed copy) only after explicit confirmation; the inventor never retypes an already-recorded reason; every non-`UNDETERMINED` confirmation still carries a recorded rationale; the original statement remains separately preserved and unchanged.
8. **Deferral is a valid state.** "Not sure yet" / "Decide later" is always available (summary-level and per item) → `UNDETERMINED`/`undetermined`; it creates no warning, no maturity penalty, no quality penalty, no IQ-like evaluation, no scoring consequence, and does not block the normal journey (unless a later, explicitly owner-approved action truly requires confirmation — none exists in this workstream). Skipping the step entirely changes nothing (`UNDETERMINED`/`system-derived`). Uncertainty is not failure.
9. **Invisible governance.** Internal concepts (category, authority, rationale, provenance, confirmation record, evidence, stale confirmation) are translated into simple natural language. Inventor-facing text never exposes: "criticality authority", "owner-confirmed", "system-derived", "undetermined authority", "rationale requirement", "evidence gate", "classification compliance", or any raw internal token.
10. **No silent adoption.** Until explicit acceptance, proposals are visibly unconfirmed, stored nowhere, rendered as owner-confirmed nowhere, and never influence the derived result. The three layers — system understanding/proposal, inventor confirmation/correction, recorded owner-confirmed result — remain contractually distinct.
